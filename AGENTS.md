## The #1 Rule: Notebook-Driven Development with nbdev

**NEVER edit `.py` files in the `{package_name}/` folder directly.** They are auto-generated by nbdev from notebooks in `nbs/`.

### What goes where

| Code type | Location | How to edit |
|---|---|---|
| Library code (classes, functions, utilities) | `nbs/*.ipynb` → auto-exported to `{package_name}/*.py` | Edit the notebook |
| Route handlers (`@rt` decorated functions) | `main.py` | Edit directly |
| UI helper functions used only in routes | `main.py` | Edit directly |
| Tests | Inline in notebooks (using `fastcore.test`) | Edit the notebook |
| Documentation | Inline in notebooks (prose cells) | Edit the notebook |

### nbdev workflow commands

```bash
uv run nbdev_export    # Export notebooks → .py modules
uv run nbdev_test      # Run all tests in notebooks
uv run nbdev_clean     # Clean notebook metadata
uv run nbdev_prepare   # All of the above + nbdev_readme
```

### Git commit workflow (mandatory)

1. Run `uv run nbdev_prepare`
2. Stage changes
3. Commit — if pre-commit hooks modify notebooks, re-stage and re-commit
4. Never bypass nbdev hooks

## Code Style: fast.ai Style Guide

### Brevity facilitates reasoning

- Keep code compact using comprehensions, lambdas, f-strings, ternary operators
- Aim to keep one semantic concept under 60 lines
- One line of code = one complete idea
- If a 1-line function body fits on the `def` line, put them together: `def det_zoom(zoom): return lambda x: zoom_cv(x, zoom)`
- If/else on one line when the body is short: `if cond: do_thing()`
- Group similar 1-line functions without blank lines between them

### Naming

- CamelCase for classes, under_score for everything else
- Short names for common things; use the abbreviations from fast.ai conventions
- `o` for objects in comprehensions, `i` for index, `k,v` for key-value pairs
- `x` for tensor/algorithm input

### Layout

- Max 160 characters per line
- Align conceptually similar statement parts vertically
- Minimize vertical whitespace — import multiple modules on one line
- Indent with 4 spaces
- Avoid trailing whitespace
- Use destructuring assignment for class member initializers: `self.sz,self.denorm = sz,denorm`

### Documentation

- Use `docments` (parameter comments right after the parameter) — this is the nbdev way
- Avoid comments unless they explain *why*, not *how*
- One-line docstrings with back-quoted references to main params

### Imports

- Use `from module import *` freely for fast.ai ecosystem packages (fastcore, fasthtml, monsterui, fastlite)
- These libraries are designed for safe wildcard imports

## Database Patterns

### SQLite with fastlite (MiniDataAPI)

```python
from fastlite import *

db = database("./data/app.db")
db.execute("PRAGMA foreign_keys = ON;")
```

### Pydantic models with SQLite serialization

Every data model follows this pattern:

1. **Pydantic BaseModel** as the primary class with full type safety
2. **`flatten_for_db()` method** to convert complex types (enums, nested models, lists) to SQLite-compatible flat dict
3. **`get_db_schema()` classmethod** returning a `@dataclass` with SQLite-friendly types (used by fastlite's `db.create()`)
4. **`from_db()` classmethod** to reconstruct the Pydantic model from a database record
5. **`_instances` ClassVar** for in-memory instance tracking when needed
6. **Computed `slug` field** via a `SluggedModel` base class for URL-friendly identifiers

```python
class MyModel(SluggedModel):
    id: int | None = Field(default=None)
    name: str = Field(...)
    
    def flatten_for_db(self): ...
    
    @classmethod
    def get_db_schema(cls): ...
    
    @classmethod
    def from_db(cls, db_record): ...
```

### Table creation

```python
create_tables_from_pydantic(db, [ModelA, ModelB])  # Uses get_db_schema() + transform=True
```

### Querying

```python
db.t.table_name()                    # All rows
db.t.table_name("slug=?", (slug,))   # Filtered query
```

## FastHTML Patterns

### App setup

```python
from fasthtml.common import *
from monsterui.all import *

app, rt = fast_app(
    hdrs=[
        Style(".node { cursor: pointer; }"),
        Theme.blue.headers(),
    ],
)
```

### Route handlers

- Use `@rt` decorator (shorthand for `@app.route`)
- Use `Titled()` for pages that need a title (wraps in Container + adds H1 + meta title)
- Use `serve()` at the end of `main.py` (no `if __name__ == "__main__"` needed)
- For form handling, use `async def` with `req` parameter and `await req.form()`

### HTMX patterns

- Use `hx_get`, `hx_post`, `hx_target`, `hx_swap` attributes on FastHTML components
- Target `#main-content` for SPA-like navigation within a page
- Use `hx_target="body", hx_swap="innerHTML"` for full page transitions
- For clickable elements that trigger navigation: add `style="cursor:pointer;"` and HTMX attributes

### MonsterUI components

- Use `Card`, `Container`, `DivFullySpaced`, `DivHStacked`, `DivVStacked`, `DivLAligned`, `DivRAligned`
- Use `ButtonT.primary`, `ButtonT.secondary`, `ButtonT.text` for button styles
- Use `LabelInput`, `LabelSelect`, `LabelTextArea`, `LabelCheckboxX` for form elements
- Use `H2`, `H3`, `H4`, `P`, `Strong`, `Hr`, `Grid` for layout
- Use `render_md()` for rendering markdown content
- Use `NavBar` for top navigation
- Use `ThemePicker()` for theme switching
- UK utility classes: `"uk-margin-bottom"`, `"uk-margin-small"`, `"space-y-2"`, `"w-full"`, `"min-w-40"`

### Error handling in routes

```python
try:
    # process form data, create/update model
    return RedirectResponse(url=f"/item?slug={item.slug}", status_code=303)
except Exception as e:
    return Titled("Validation Error",
        Card(
            P(f"Error: {str(e)}"),
            Button("Back", hx_get="/previous_page", hx_target="#main-content", hx_swap="innerHTML")
        )
    )
```

## Process Rules

### Working approach

1. Work in small steps — one feature or one bug at a time
2. Always prefer simple solutions
3. Avoid duplication — check for existing similar code first
4. When fixing bugs, exhaust existing patterns before introducing new ones
5. Never mock data for the actual application (only for tests)
6. Use type hints for all code
7. Use docments for parameter documentation

### Branch management

- Create a new branch for every new feature or issue
- Ask to create a branch if the task will change >40 lines or add >20 lines

### When choosing between implementations

If multiple solutions exist, explain why you chose one over the others.

### Checking library documentation

Before writing code using FastHTML, MonsterUI, fastcore, or nbdev, consult the relevant documentation in the `aicontext/` folder. Follow any links to more detailed docs when the task has multiple possible implementations.

## Testing

- Write tests using `fastcore.test` module (`test_eq`, `test_ne`, `test_close`, etc.)
- Tests live inline in the notebooks, right after the code they test
- Run with `uv run nbdev_test`

## Deployment

### Dockerfile pattern

```dockerfile
FROM ghcr.io/astral-sh/uv:python3.12-trixie-slim
WORKDIR /app
RUN apt update && apt install -y {system-deps}
COPY pyproject.toml uv.lock .
RUN --mount=type=cache,target=/root/.cache uv sync --no-install-project
COPY . .
RUN --mount=type=cache,target=/root/.cache uv sync
EXPOSE 5001
CMD ["uv", "run", "main.py"]
```
